# Modern Web Guidance in Product Design

Run this required stage after identifying the user jobs and before selecting or critiquing a design. Use the official [Google Chrome Modern Web Guidance](https://developer.chrome.com/docs/modern-web-guidance) corpus. Use the shared [Workbench launcher instructions](../../frontend-project-fit/references/modern-web-guidance.md) for every CLI call so telemetry stays off.

## Ask about the user job

Identify the unresolved choices that can change a user outcome. Start from what users must do, what else they need to see or use at the same time, and the narrowest relevant viewport or container. Include the open composition and interaction decisions, not only the easiest control to name. A design about type or color can search the corresponding readability, contrast, theme or hierarchy constraint. An authorized locked choice needs a compatibility or critique check, not a manufactured debate.

Search with short English phrases for one capability at a time, then retrieve the full relevant guides and read their decision criteria, alternatives and browser constraints. A result title or description is discovery, not consultation. If a result is materially relevant but cannot be opened, record the gap. Rephrase a weak search once. Consider closely related results for genuinely open alternatives. Use the published catalog to locate full guides if the CLI cannot run. Inspecting actual installed official guides or the exact official distribution online completes the lookup when the CLI is unavailable.

## Decide on fit

Use MWG's conditions in context. Read through the alternatives in a retrieved guide before adopting its default. For example, whether the original view must stay usable comes before selecting a modal. The number of filter choices is one input alongside frequency, the space needed by other controls, and what remains visible at narrow widths. Navigation guidance helps implement a shell once real destinations, context and scope justify it.

A guide can support, constrain, or be inapplicable to a choice. Existing product conventions, accessibility, browser support, and the user's authority still govern. A guide that proposes a new action is not permission to add it. Search that succeeds but finds no relevant guide can be recorded as `no-match`; use appropriate primary evidence for the affected platform question. Failure to access MWG through the CLI, installed guides, and official distribution is `unavailable`. Keep affected work provisional in that case. Respect an explicit user restriction on tool or network access, use any permitted MWG source, and state the resulting evidence limit.

## Keep the evidence with the decision

Before locking direction or handing it off, capture one compact record per material question in the existing rationale or approved handoff. Include question, consulted MWG version or immutable source, query or catalog lookup, full guide IDs or explicit outcome, relevant rule or alternative, chosen behavior and why, and an observable check. Link primary evidence if it filled a documented gap. In a bounded critique, keep this in working context. Reuse records only while the question, constraints and supported browsers still match. Pass visible effects into the design brief and applicable browser or fallback obligations to Project Fit. Keep URLs, lookup traces and rejected options out of UI copy and renderer prompts.
