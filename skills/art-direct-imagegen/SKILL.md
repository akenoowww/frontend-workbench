# Art-Direct ImageGen

Translate a Product Design-owned visual direction into the requested bitmap outputs and report their status truthfully. This skill owns renderer briefs, ImageGen calls, bitmap-specific review, continuity, and accepted-image delivery—not upstream concept, product behavior, IA, copy, routes, code, or implementation. Its renderer prompt is an art-direction envelope, never a composed screen specification: ground it in one specific relationship and a coherent aesthetic role system, while leaving composition, geometry, and visual mechanism open. A familiar implemented pattern is valid when current evidence and task fit support it; escaping an unsupported default does not require novel interaction topology. Every run uses Frontend Product Design as the direction owner; there is no independent renderer-owned direction fallback. The final assembly of reviewed scroll bands uses a preservation-first compositing brief; it does not reopen art direction.

## Render scrolling pages in stages

For a landing page, storefront, or other page with successive content sections, generate the necessary full-size scroll bands serially. Assemble reviewed bands through ImageGen when one continuous complete-page image is a required deliverable; a set of separate page/state design images needs no extra composite unless requested. Each band uses the full target desktop width and a normal viewport-height canvas; its own content fills that canvas at a readable UI scale. Do not shrink the complete page into one tall render, use a thumbnail strip, or squeeze all sections into the hero. Plan enough bands to cover the complete requested content; one final PNG, one homepage, a preview-only request, or sparse copy does not authorize skipping these stages. Derive band count from section jobs and legibility, not a fixed count or fewer calls.

A genuinely single-screen UI/hero may use one render. A one-call tall overview is allowed only when the user explicitly requests that generation method; record the exception before rendering. A tall image produced by final assembly is the normal delivery, not that exception.

## Choose the workflow profile

- **MICRO** — only when the complete requested design fits one independent readable output with a fixed objective and no dependency, approval checkpoint, durable resume, promotion gate, or downstream fidelity gate. Render and review it without initializing the full runtime.
- **STANDARD** — the complete task-derived output set needing art direction and bounded iteration, but no staged implementation contract. Its size follows necessary coverage, not a default numeric or “small set” quota. This includes a preview-only, non-promotable redesign with a frozen target, boundary, references, outputs and call budget, without implementation or durable acceptance. Product Design derives that set; the user need not enumerate outputs. Render one output per call and preserve files through the system ImageGen path rules.
- **FULL** — dependent/coherent outputs that carry user acceptance or downstream authority, page-by-page approval, a complete/material redesign intended for implementation, durable resume/promotion, or a design-to-implementation fidelity contract. Use workflowProfile full and the runtime state machine.

If the request is only analysis, exit this skill. Route non-UI imagery and a fixed surgical bitmap edit to the system imagegen workflow without inventing product design. A planned frontend page assembly remains the final output of this workflow and uses the same built-in renderer. Escalate from MICRO/STANDARD only when a FULL criterion appears.

## Derive the complete design set

Use Product Design's current visual/functional baseline, selected direction and source-to-destination capability map. Plan separate readable outputs for each materially distinct designed area, page state, scroll band or required viewport that communicates the complete described page/flow and its logical reallocations. Different states on one route are different outputs, not repeated attempts at one image. Group equivalent states and repetitive records when representative evidence proves the same design; do not generate every permutation or extra alternative concepts.

Choose the profile after coverage is known. One user-described page does not imply one ImageGen call. Derive the initial budget from the actual required outputs, any requested complete-page assembly and explicitly allowed retries. Honor explicit user cost/output limits by resolving a real coverage conflict instead of silently omitting functions. No fixed page count, state/control type, reference count or image quantity is a default recipe; examples test the rule rather than define it.

Current-page images and eligible external UI examples may both be scoped inputs when Product Design declares their roles and influence. The current product owns functional/semantic truth; external images contribute selected principles. Use reviewed preceding output pixels when another state must preserve the same underlying page, with a named preserve/change-only delta. Keep existing exposure, source-role, direction, provenance and creative-freedom rules. Do not copy a foreign feature set or replay an unrelated screenshot as a layout template.

## Required Product Design dependency

Read and apply the actual [Frontend Product Design skill](../frontend-product-design/SKILL.md), not only one of its references, before every render workflow. If its current scoped direction and evidence were already established in this task, reuse them and perform only the applicable ownership/freshness validation; do not restart design, repeat research for each band, or mutate the lock.

When entering from a standalone frontend UI bitmap request, use Product Design in a **direction-only entry**: it performs the required current working-product research, resolves the authorized hierarchy/behavior and visual direction, freezes the applicable boundary and output scope, and returns the pre-render direction handoff. The request for the bitmap authorizes this necessary design step. A bounded independent preview normally uses Product Design STANDARD without implementation or durable FULL authority; existing material-redesign and FULL criteria still govern. The renderer's own MICRO/STANDARD profile need not initialize a FULL session merely because it uses Product Design.

While servicing this entry, Product Design returns to the same Art-Direct caller rather than invoking another renderer or generating a second output. Product Design retains direction and shared conceptual critique ownership; Art-Direct resumes prompt compilation and the original render once. After the bitmap exists, perform the applicable shared critique under Product Design. This handoff does not grant new pages, controls, copy, code, or implementation authority. If the Product Design skill, required evidence, or usable handoff is unavailable, report BLOCKED instead of synthesizing a substitute direction.

## Choose the contract mode

Both entry modes use the Product Design dependency above. Its current-product research applies to standalone UI direction in every profile. Generic trend rules, product names, or unverified old screenshots cannot substitute. In **UPSTREAM CONTRACT**, consume its verified current-product evidence and locked direction rather than repeating research or redesigning it; a material missing-evidence gap returns to Product Design.

- **UPSTREAM CONTRACT** — consume the supplied objective, locks, direction, content, reference scope, and delivery requirements. FULL v3 additionally requires product/scenario/shell identities, scoped `referenceBindings`, declared design-evidence outputs, and any applicable render budget. Treat supplied direction, page, state, viewport, content, and product decisions as fixed. A material upstream render without a required locked direction is blocked and returns to Product Design.
- **STANDALONE ENTRY** — extract only the user's explicit content, references, constraints, and requested outputs, then obtain the bitmap-scoped direction from the actual Product Design skill through the direction-only entry above. A complete/material redesign normally uses Product Design and FULL. The preview-only STANDARD exception remains non-promotable and must be rebound through Product Design/FULL before downstream implementation or durable acceptance. Standalone describes how the user entered the workflow, not independent renderer design ownership. Block on an unresolved product decision.

Label supplied images FUNCTIONAL_REFERENCE, STYLE_REFERENCE, EDIT_TARGET, or VISUAL_ANCHOR. Apply each only through applicable `referenceBindings` entries and their surfaces/aspects; never silently treat a functional reference as an edit target or let a module reference replace an inherited shell. A `FUNCTIONAL_REFERENCE` is analysis evidence by default, not automatically a renderer input. When its scoped behavior, content, and relationships can be carried completely as text truth, keep its bytes out of the ImageGen call so its incidental style cannot anchor the result. Pass source bytes only when an explicitly bound exact visible invariant or relationship cannot be represented faithfully otherwise; expose the narrowest applicable region and state both what may and must not influence the result.

## Render

1. **Validate the current output.** MICRO/STANDARD need the bounded objective, complete planned coverage set, current output, applicable inputs/roles, direction, content, and delivery path. FULL additionally confirms stable output/surface/state/viewport identity, required design evidence, artifact kind, shell/reference IDs, direction SHA, approval/promotion fields, and remaining render budget. Product Design/IA may allocate content logically to authorized pages/states before freezing the plan; the renderer cannot invent destinations or extra states after handoff. Do not render runtime-only coverage.
2. **Resolve direction ownership.** Use Product Design's pre-render handoff in both modes. For UPSTREAM CONTRACT, validate and preserve the locked direction; for STANDALONE ENTRY, validate the newly returned bitmap-scoped direction before prompting. A usable direction gives ImageGen one product-specific perceptual relationship among the primary object, supporting evidence, and supplied actions, plus a clear attention hierarchy and coherent aesthetic roles. When structural or relational presentation is material, it also fixes a renderer-neutral representation grammar: context model, relation carrier, focus transition, and entity embodiment. A carrier metaphor or material/style vocabulary alone is not a direction. An unsupported generic completion is too weak; a mature implemented pattern justified by current evidence remains valid. Fewer than two materially different feasible compositions indicates excessive prescription. If the positive relationship conflicts with its own avoid list or supplied semantics, return to Product Design to resolve it; the renderer must not rewrite the concept. Keep candidate work and the direction decision record out of the renderer prompt.
3. **Start the right execution path.** MICRO/STANDARD do not initialize the full checkpoint runtime. FULL validates or resumes the active .frontend-workbench session before any expensive call and follows the state machine in full-runtime.md.
4. **Render serially.** Make one built-in ImageGen call for one output. Never use parallel calls, n, a multi-state collage, or subagents for connected deliverables. A planned assembly call takes several source images and produces one continuous page; it is one output, not a collage. MICRO allows exactly one call. STANDARD may render a frozen coverage set in the same user turn when upstream IA/Product Design determines the full-size scroll bands, page-family screens, or related outputs needed for faithful coverage. The user need not enumerate those outputs; the in-scope request authorizes necessary decomposition, while optional variants or alternative concepts still require explicit authorization. Before the first call, freeze every output ID, order, semantic responsibility, content allowlist, delivery path, total call ceiling, and the set choreography defined in [references/output-contract.md](references/output-contract.md), including `artifactTopology: separate-bands` for scrolling pages (`single-tall` only for an explicitly requested one-call overview), `continuityRequirement: system-coherent | authored-breaks | seamless-page`, canvas role/target aspect, shell ownership/chrome, transition mode, and reference exposure. Derive band count from legibility, hierarchy, section jobs, scroll semantics, and downstream evidence. A general request for a page or final image must use staged bands; do not infer the one-call exception from the desired final file count. Choose the final delivery method before freezing the set: ImageGen by default for one continuous page, or local-only when explicitly requested. Only the ImageGen method adds a final assembly output and one additional built-in call per page; its content allowlist is the ordered union of its source bands. For separate bands, generated imagery slots are unique unless explicitly shared, and each continuation inherits the root shell without restarting it. Use the least contaminating reference exposure that can carry the declared invariant: no image when the locked textual direction is sufficient; a scoped region or deterministic system capsule when exact type/material/boundary evidence is needed but imagery/layout must stay unique; the accepted full immediate predecessor only when an exact continued spatial, structural, or shell relationship itself must survive and is compatible with the current imagery policy. Type, palette, material, or mood roles alone do not justify full-screen exposure. Record what every reference may and must not influence; never reuse one distant root artifact as a catch-all anchor for later bands. Only for an explicitly requested one-call overview, record that method authorization and render `single-tall` with its agreed overview scale; do not misreport it as a viewport capture. Do not add outputs or switch topology after rendering begins. A known failed render or failed bitmap review ends the attempt as `REVISE_ARTIFACT`; an unknown provider outcome or missing result evidence is `BLOCKED` and must be reconciled before another call; do not issue another `Create` call for that output or continue to later outputs. FULL retries require a successful render-budget reservation. A long page uses separate `top` and continuation outputs followed by its selected assembly method unless the user explicitly chose a one-call overview; never compress content merely to reduce call count. Before each call, treat the current output's `contentIds` as its visibility allowlist: no other output's metric, label, status, action, source fact, or unique imagery slot may enter the prompt unless explicitly shared or the frozen single-tall/assembly range owns it. Global product truth is a preservation constraint across the complete product, not an instruction to render every fact in this bitmap. Ordering dependencies do not imply visual continuity. When `anchorOutputId` is non-null, use only its accepted artifact bound by `anchorArtifactSha256` and verify the renderer brief's preserve/change-only delta plus current direction, shell, content-distribution, set-choreography, and reference identities before the call.
5. **Review before acceptance.** Check bitmap and output-contract fidelity first, then apply the shared first-artifact critique when this is the representative artifact for the direction. For every FULL output with `artifactKind: imagegen`, attach the helper-verified provenance receipt before review regardless of the overall artifact policy. On a later user-authorized retry, edit the saved failed artifact itself; keep all supplied input roles immutable and never promote a `STYLE_REFERENCE` or `FUNCTIONAL_REFERENCE` to `EDIT_TARGET`. Return upstream `REVISE_DIRECTION` or `BLOCKED` without silently changing a locked concept.
6. **Deliver truthfully.** Save accepted artifacts through system ImageGen rules. Promote a project-bound FULL artifact only through the runtime helper. Preview-only output may remain in allowed task storage.
7. **Assemble a required continuous-page deliverable.** If the requested result includes one continuous complete-page image and its frozen assembly method is ImageGen, pass the reviewed scroll-band images in order to a final built-in ImageGen call using [references/output-contract.md](references/output-contract.md). A set of separate design/state images needs no extra assembly unless that composite is also required. Preserve design/content; limit changes to declared joins and overlap. This separately planned, budgeted output needs its own review and provenance. Review combined pixels for content fidelity, shell lineage, dimensions, typography, imagery, scroll rhythm and continuity before PASS; deliver the sources alongside it. An explicit one-call overview needs no assembly call. An explicit local-only composite is reviewed under that method without an ImageGen assembly; a local comparison does not discharge a requested ImageGen result. Assembly failure ends the attempt; do not silently substitute a method or add generative repairs.

## Keep prompts and status lean

For final assembly, use the compositing template in [references/prompt-and-review.md](references/prompt-and-review.md). For each original band/page render, compile one prompt for one visible output: ID/type, immediate purpose, applicable render-time reference bindings/input roles, only the current band's content IDs and critical short labels, the relevant locked direction relationship, only the representation-grammar fields needed for this output, continuity locks, creative latitude, and at most three causal avoid items. For a coherent boundary, compile its frozen exit/entry states, handoff carrier, edge treatment, and transition mode into one non-geometric perceptual relationship; keep the raw field names, edge geometry, and mechanism in the review ledger so ImageGen retains compositional freedom. When supplied meaning is relational, carry each applicable relation as a compact semantic triple such as `subject —predicate→ object`; disconnected labels are not enough. When multiple supplied sets have no declared relation, keep them semantically independent and do not imply pairing through count, order, proximity, or repeated alignment. This preserves product truth without prescribing placement, connector geometry, or exact topology. Translate thesis or metaphor language into a nonverbal perceptual relationship; do not send slogan-like, caption-ready, or explanatory prose that ImageGen could render as product copy. Keep exact redesign thresholds and `forbiddenCarryover` in the review ledger; translate each replace region into one positive perceptual departure for the renderer instead of echoing rejected source topology, colors, components, or visual devices under negation. Do not turn a reviewer's example, a previous artifact, or an internally rejected idea into a new visual target or negative anchor unless the user explicitly locks it; encode the underlying quality failure instead. For progressive scroll, perform a literal prompt-to-band check before the expensive call: remove every label, value, action, and status owned by another band, and do not disguise repetition through “summary” versus “detail” aliases. Exclude the full direction/global contract, rejected concepts, other outputs, product reasoning, implementation instructions, and long copy.

For MICRO, report `PASS`, `REVISE_ARTIFACT`, `REVISE_DIRECTION`, or `BLOCKED` after its one call without pretending it is a durable checkpoint. For STANDARD, render the complete frozen required set serially in the same user turn: review each output before continuing, then report set coverage and verdict. Stop for a failed/unknown outcome, a real budget/scope conflict or a requested approval checkpoint, not merely because one image exists. User feedback permits a bounded attempt on the affected failed output, not an autonomous retry chain; use its saved artifact and one delta. Direction changes return to Product Design without silently adding outputs. FULL follows runtime transitions: internally reviewed anchors may continue when their contract does not require per-output user approval; explicit output/stage checkpoints remain blocking. Never regenerate accepted/promoted work or report success with required coverage unfinished. Under `imagegen-required`, exact user authorization of the complete required design set and direction still precedes implementation or durable promotion; internal review is not that authorization. Runtime-only outputs remain for Runtime QA.

Generated UI is an instance of visual direction, not the direction contract, component specification, runtime evidence, or implementation proof. It may express project-specific hierarchy without requiring custom controls; Project Fit chooses mature implementation capabilities. Record the direction reference/SHA, output status, accepted/promoted paths, anchor identity when applicable, budget use, critique verdict, and final prompt set. A bitmap-scoped Product Design handoff remains preview-only until Product Design explicitly validates its downstream scope and authority.

Keep technical receipts, hashes, prompts, and research traces in the authorized artifact/handoff; expose them when needed for a checkpoint, requested technical review, or recovery. Ordinary delivery leads with the image, the considered design recommendation, concrete reasons, and material limitations, without narrating plugin internals or search locations. Respectfully challenge user proposals that would harm the task or readability, offer a feasible alternative, and distinguish supported usability constraints from aesthetic preference. Never pretend missing research or rendered evidence exists.

Do not volunteer competitor names or a source-by-source comparison merely to legitimize a normal design recommendation. Present the choice as your considered judgment; show named examples and sources when requested or needed for a specific external fact, with accurate attribution. Keep the mandatory research trace available without turning it into unsolicited delivery copy.
